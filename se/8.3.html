8.3 MCP 協定：跨國企業系統互聯的新標準

🏆 ERP 旗艦專案・模組 8：AI 對話查庫存與下單 本節產出：把進銷存試算表發布成 Web App，再用一支小型 MCP 伺服器包裝成兩個工具，讓 AI 助手一句話查庫存、經你確認後下單。

學完本節，你能夠：

  1. 用「N×M 變 N＋M」說明 MCP 解決的問題，並正確區分 MCP 的 Host、Client、Server，以及 Tools、Resources、Prompts 三種能力。
  2. 把 Google 試算表發布為 Web App，並用 MCP 伺服器包裝成 check_erp_inventory、create_sales_order 兩個工具，接上支援 MCP 的 AI 助手。
  3. 為 Web App 設定存取密鑰（token），實際示範「繞過 MCP 直接呼叫 Web App」時哪一層擋下請求，並說明共用密鑰的限制。

壹、開場情境：人在高鐵上，客戶在等答案

📌 以下為教學情境（依實務改編）。

營運經理坐在往台北的高鐵上，台中經銷商傳來訊息：「A 款鍵盤這週能不能再出 25 台？單價照上次 NT$ 4,200。」

答案就在第 4.2 節做好的進銷存試算表裡，但用手機打開試算表、找到「庫存主檔」、再切到「銷售訂單」新增一列，既慢又容易點錯。經理真正想做的是對 AI 助手說一句：

「A 款還有幾台？夠的話幫台中經銷商下 25 台，單價 4,200。」

問題是，AI 助手碰不到你的試算表。就算資訊組幫某一個 AI 工具寫了專用外掛，明年公司換用另一套 AI 工具，外掛又得重寫一次。

本節要解決的問題： 能不能讓試算表「只接一次」，之後任何支援標準的 AI 助手都能安全地查庫存、下訂單？

貳、為什麼會這樣：N×M 的整合問題與 MCP

1. 從 N×M 到 N＋M

假設公司有 3 種 AI 工具（例如 Antigravity、Claude、Cursor）和 4 個業務系統（ERP、CRM、雲端硬碟、物流 API）。如果每一對都要寫一套專用串接：

做法 需要寫幾套串接 換掉一個 AI 工具時
各自串接 3 × 4 ＝ 12 套 跟它有關的 4 套全部重寫
共用一個標準 3 ＋ 4 ＝ 7 個（每個 AI 工具支援標準一次、每個系統包裝一次） 新工具只要支援標準就能直接用

這就像 USB-C：手機廠和充電器廠各自遵守同一個規格，就不需要每支手機配一條專用線。

MCP（Model Context Protocol，模型上下文協定） 就是 AI 世界的這種規格。它是 Anthropic 在 2024 年 11 月發布的開放協定，2025 年起 OpenAI、Google（Gemini）、Microsoft 等主要廠商的產品陸續支援；2025 年 12 月，Anthropic 將 MCP 捐贈給 Linux 基金會旗下新成立的 Agentic AI Foundation，由中立組織治理。

2. 三個角色與兩種連線方式

角色 是什麼 本節中
Host（主機） 使用者操作的 AI 應用程式；內含與各 Server 一對一連線的 Client 元件 Antigravity 或其他支援 MCP 的 AI 助手
Client（用戶端） Client 是 Host 內部的連線元件，每個 Client 與一個 Server 一對一連線 Host 為 erp_mcp_server.py 建立的那一條連線
Server（伺服器） 把某個系統的能力依 MCP 規格包裝起來的小程式 本節的 erp_mcp_server.py

雙方用 JSON-RPC 2.0（用 JSON 表達「呼叫哪個功能、帶什麼參數」的格式，JSON 見 4.3 節）交換訊息。標準連線方式有兩種：stdio（Host 在你的電腦上直接啟動 Server 程式，本節採用）與 Streamable HTTP（Server 是遠端網路服務，取代早期的 HTTP＋SSE 方式）。

3. Server 能提供的三種能力

能力 用途 由誰決定使用 ERP 例子
Tools（工具） 讓 AI 執行動作：查詢、計算、寫入 AI 模型判斷何時呼叫（Host 通常會先請使用者同意） check_erp_inventory、create_sales_order
Resources（資源） 提供可讀取的資料，以 URI 識別 由 Host 應用程式或使用者決定附加哪些資料給 AI 一份「本月價目表」文件
Prompts（提示範本） 預先寫好的工作範本 使用者主動選用（例如從選單或斜線指令挑選） 「每週庫存檢討」報告範本

本節只用到 Tools。第 8.1 節寫的工具名稱、說明與參數規格，在 MCP 裡原封不動地派上用場：Host 連上 Server 後，會先詢問「你有哪些工具？」（tools/list），取得每個工具的名稱、說明與 inputSchema，AI 再依此決定要不要呼叫（tools/call）。

⚠️ MCP 規格對人工確認的態度 MCP 規格建議：工具呼叫應該始終有人在迴路中，使用者要能拒絕。多數 Host 在 AI 呼叫工具前會跳出確認視窗。不要為了方便，把會寫入資料的工具設成「永遠自動允許」。

參、把規則寫下來

把開場那句話翻成兩個工具的規格（延續第 8.1、8.2 節）：

經理說的話 需要追問的問題 寫成規格
「A 款還有幾台？」 經理只會說「A 款」，不會說完整品名 check_erp_inventory(item_name)：用關鍵字查詢，回傳完整品名、庫存、加權成本、安全庫存、狀態；第①類唯讀
「幫我下 25 台」 下單用關鍵字可以嗎？ create_sales_order 必須用完整品名（ERP 用完全相同比對）；第④類寫入
「單價 4,200」 幣別？可以是 0 嗎？ 新台幣，> 0
（經理沒說） AI 一次最多能代下幾台？ 1～100 的整數（MAX_ORDER_QTY），超過走人工
（經理沒說） 下單前要不要再確認？ 必須先向使用者複述客戶、品名、數量、單價並取得同意
（經理沒說） 連不上試算表怎麼辦？ 回報錯誤並停止，不得猜測庫存數字；下單時連線中斷要提醒「訂單是否成立未知」
（經理沒說） 誰可以呼叫這個 Web App？ 必須帶正確的存取密鑰 token（存在 Apps Script 的指令碼屬性 API_TOKEN）；沒帶、帶錯、或管理者還沒設定密鑰，一律拒絕
（經理沒說） 有人繞過 MCP 直接送負數怎麼辦？ 後端 apiSubmitSalesOrder() 自己再檢查一次：數量必須是大於 0 的整數、單價大於 0

肆、讓 AI 做出來

1. 整體架構：兩層包裝

  • 第一層：GAS Web App。 讓試算表能被網路呼叫。這部分已經寫在 ERP_Full_System.js 的 doGet() 與 doPost() 裡，你只需要部署。
  • 第二層：MCP Server。 把 Web App 包裝成有名稱、說明、參數限制的標準工具。這部分本節要請 AI 產生。

為什麼不直接把 Web App 網址丟給 AI？因為網址本身沒有「說明」和「參數規格」：AI 不知道何時該用、該帶什麼參數，也沒有任何防呆。MCP Server 就是第 8.1 節 ACI 原則的落地處。

2. 最小必要概念：Web App

概念 白話說明
Web App（網頁應用程式） 把 Apps Script 部署成一個網址（結尾是 /exec），外部可以用 HTTP 呼叫它
doGet(e) 有人用 GET（讀取）呼叫網址時執行；網址後面的參數在 e.parameter 裡
doPost(e) 有人用 POST（送出資料）呼叫時執行；送來的內容在 e.postData.contents

token（存取密鑰） 一串只有你和 MCP Server 知道的隨機文字；Web App 只接受帶著正確 token 的請求

3. GAS 後端（ERP_Full_System.js 既有程式碼，不需修改）

// 模組 8（8.3）：Web App API (doGet / doPost)，須帶正確 token
// 產生並儲存 Web App 存取密鑰（在編輯器手動執行一次；密鑰外流時再執行一次即可換新）
function setupApiToken() {
  const token = Utilities.getUuid().replace(/-/g, '');
  PropertiesService.getScriptProperties().setProperty(API_TOKEN_PROPERTY, token);
  showMessage_('🔑 已產生新的 Web App 存取密鑰（舊密鑰立即失效）：\n\n' + token +
    '\n\n請存入 MCP Server 的環境變數（例如 ERP_API_TOKEN），不要貼在聊天室或程式碼裡。');
}

// 檢查密鑰：未設定密鑰時一律拒絕（fail-safe），而不是「沒設就不檢查」
function isAuthorized_(token) {
  const expected = PropertiesService.getScriptProperties().getProperty(API_TOKEN_PROPERTY);
  if (!expected) return false;
  return typeof token === 'string' && token === expected;
}

function jsonOutput_(obj) {
  return ContentService.createTextOutput(JSON.stringify(obj))
    .setMimeType(ContentService.MimeType.JSON);
}

const UNAUTHORIZED_ = { success: false, error: '未授權：缺少或錯誤的 token（請洽系統管理員）' };

function doGet(e) {
  const params = (e && e.parameter) || {};
  if (!isAuthorized_(params.token)) {
    // 沒有 action 的網頁請求也要密鑰：入口網頁可以下單，不能讓拿到網址的人直接用
    return params.action ? jsonOutput_(UNAUTHORIZED_)
      : HtmlService.createHtmlOutput('<p>🔒 未授權：請使用含正確 token 的網址開啟。</p>');
  }

  // 沒有 action 參數：顯示業務行動填單網頁
  if (!params.action) return getSalesPortalHtmlOutput();

  const result = { success: false, data: null, timestamp: new Date().toISOString() };
  const stockSheet = SpreadsheetApp.getActiveSpreadsheet().getSheetByName(SHEET_STOCK);

  if (params.action !== 'checkStock') {
    result.error = '不支援的 action：' + params.action;
  } else if (!stockSheet) {
    result.error = '系統未初始化，找不到「庫存主檔」';
  } else {
    const queryItem = params.item;
    const items = [];
    for (const [item, qty, cost, safety, status] of readRows_(stockSheet, 5)) {
      if (!item) continue;
      // 關鍵字比對：查「A款」會找到「人體工學鍵盤 A款」
      if (!queryItem || String(item).includes(queryItem)) {
        items.push({
          itemName: String(item),
          availableStock: Number(qty),
          unitCostEur: Number(cost),
          safetyStock: Number(safety),
          status: status
        });
      }
    }
    result.success = true;
    result.data = items;
  }
  return jsonOutput_(result);
}

function doPost(e) {
  let payload = {};
  try {
    payload = JSON.parse(e.postData.contents);
  } catch (err) {
    return jsonOutput_({ success: false, error: 'Invalid JSON' });
  }

  // 密鑰可放在網址 ?token=...，或 JSON 內容的 token 欄位（GAS 讀不到自訂 HTTP 標頭）
  const token = (e.parameter && e.parameter.token) || payload.token;
  if (!isAuthorized_(token)) return jsonOutput_(UNAUTHORIZED_);

  // 只取下單需要的欄位，交給與業務入口網頁相同的下單函數（防呆、防超賣、扣庫存都在裡面）
  const result = apiSubmitSalesOrder({
    customer: payload.customer,
    item: payload.item,
    quantity: payload.quantity,
    unitPriceTwd: payload.unitPriceTwd
  });
  return jsonOutput_(result);
}

  if (!(Number.isInteger(orderQty) && orderQty > 0)) {

  if (!(unitPrice > 0)) {

注意四件事：

  • 先驗密鑰，再做事。 isAuthorized_() 在管理者還沒設定 API_TOKEN 時回傳 false，也就是「沒設定就全部拒絕」，而不是「沒設定就不檢查」。這是第 1.3 節 fail-safe 原則的資安版本。
  • doPost 沒有自己寫下單邏輯，而是呼叫第 4.2 節的 apiSubmitSalesOrder()。業務手機網頁、CRM 和 AI 走同一道關卡（數量與單價檢查、上鎖、防超賣），規則只需要維護一份。
  • 查詢用「包含」比對（includes），下單函數用「完全相同」比對（===）。這就是第參段規定「下單前先查庫存取得完整品名」的原因。
  • 密鑰放在網址參數或 JSON 內容裡，因為 GAS 的 doPost(e) 讀不到自訂的 HTTP 標頭。

4. 給 AI 的 Prompt（產生 MCP Server）

你是熟悉 Model Context Protocol（MCP）的 Python 工程師。請用官方 Python SDK（套件 mcp）寫一支 stdio 傳輸的 MCP 伺服器。

【既有後端】GAS Web App，網址從環境變數 ERP_WEBAPP_URL、存取密鑰從環境變數 ERP_API_TOKEN 讀取：
- 每個請求都要帶 token：GET 放在網址參數 token，POST 放在 JSON 內容的 token 欄位；
  token 錯誤時回傳 {success:false, error:'未授權…'}。
- 查庫存：GET ?action=checkStock&item=關鍵字&token=密鑰 → {success, data:[{itemName, availableStock, unitCostEur, safetyStock, status}]}
- 下單：POST JSON {customer, item, quantity, unitPriceTwd, token} → {success, orderId, remainingStock} 或 {success:false, error}
- Web App 對 POST 會回 302 轉址，必須跟隨轉址。

【工具與規則】
1. check_erp_inventory(item_name)：唯讀；說明寫明「下單前必須先用本工具取得完整品名」。
2. create_sales_order(customer, item_name, quantity, unit_price_twd)：quantity 為 1～MAX_ORDER_QTY 的整數，
   unit_price_twd > 0；說明寫明「會改變帳務資料，呼叫前必須向使用者複述內容並取得同意」。
3. MAX_ORDER_QTY = 100、逾時 30 秒，宣告為最上方常數；用工具註記標示唯讀／非唯讀。

【例外處理】未設定網址或密鑰、或連線失敗：回傳 success:false 與錯誤原文，提示「不要猜測庫存數字」，不得回傳預設值；
下單時連線失敗要提示「訂單是否成立未知，請人工確認」。密鑰不可寫死在程式碼中，也不可出現在回傳給 AI 的內容裡。

【輸出要求】單一檔案 erp_mcp_server.py，中文註解，相容 mcp 1.x 與 2.x（2.x 將 FastMCP 改名為 MCPServer）。

5. AI 產出的程式碼（已人工驗收）

"""
ERP MCP 伺服器（模組 8）：把 GAS Web App 包裝成 AI 可呼叫的兩個工具
執行方式：由 Antigravity 等 MCP 客戶端以 stdio 方式自動啟動，不需手動執行
"""
import os
from typing import Annotated

import requests
from mcp.types import ToolAnnotations
from pydantic import Field

try:  # mcp 2.x
    from mcp.server.mcpserver import MCPServer
except ImportError:  # mcp 1.x 舊版名稱
    from mcp.server.fastmcp import FastMCP as MCPServer

# ===== 商業規則（經理人只需要改這裡）=====
MAX_ORDER_QTY = 100      # AI 單筆可代為下單的數量上限，超過請走人工流程
TIMEOUT_SECONDS = 30     # 等待試算表回應的秒數上限

WEBAPP_URL = os.environ.get("ERP_WEBAPP_URL", "")  # 部署後取得的 .../exec 網址
API_TOKEN = os.environ.get("ERP_API_TOKEN", "")    # 與 Apps Script 指令碼屬性 API_TOKEN 相同的密鑰

mcp = MCPServer("erp")


def _fail(message: str) -> dict:
    """統一的失敗格式：告訴 AI 發生什麼事、下一步該怎麼做"""
    return {"success": False, "error": message,
            "next_step": "請把錯誤原文告訴使用者，不要猜測庫存數字。"}


def _missing_config() -> str:
    """檢查連線設定；缺少時回傳錯誤說明（不顯示密鑰內容）"""
    if not WEBAPP_URL:
        return "尚未設定 ERP_WEBAPP_URL，無法連線試算表。"
    if not API_TOKEN:
        return "尚未設定 ERP_API_TOKEN，ERP 會拒絕所有請求。"
    return ""


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))   # 第一類：唯讀查詢
def check_erp_inventory(
    item_name: Annotated[str, Field(min_length=1, description="品名關鍵字，例如「A款」")],
) -> dict:
    """查詢 ERP「庫存主檔」：回傳符合關鍵字的品項之完整品名、即時庫存、
    加權單位成本（歐元）、安全庫存與庫存狀態。唯讀，不會改變任何資料。
    下單前必須先用本工具取得「完整品名」。"""
    if problem := _missing_config():
        return _fail(problem)
    try:
        r = requests.get(WEBAPP_URL,
                         params={"action": "checkStock", "item": item_name, "token": API_TOKEN},
                         timeout=TIMEOUT_SECONDS)
        r.raise_for_status()
        return r.json()
    except Exception as e:  # 連線失敗就停止，不提供任何猜測值
        return _fail(f"無法連線 ERP：{e}")


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=False, idempotentHint=False))  # 第四類：寫入異動
def create_sales_order(
    customer: Annotated[str, Field(min_length=1, description="客戶名稱")],
    item_name: Annotated[str, Field(min_length=1, description="完整品名，須與 check_erp_inventory 回傳的 itemName 完全相同")],
    quantity: Annotated[int, Field(ge=1, le=MAX_ORDER_QTY, description="銷售數量（整數）")],
    unit_price_twd: Annotated[float, Field(gt=0, description="銷售單價（新台幣）")],
) -> dict:
    """在 ERP「銷售訂單」新增一筆訂單並立即扣減「庫存主檔」。
    會改變正式帳務資料：呼叫前必須先向使用者複述客戶、品名、數量、單價並取得同意。
    庫存不足時 ERP 會拒絕並回傳現有庫存。"""
    if problem := _missing_config():
        return _fail(problem)
    payload = {"customer": customer, "item": item_name,
               "quantity": quantity, "unitPriceTwd": unit_price_twd,
               "token": API_TOKEN}  # 密鑰放在 JSON 內容，不留在網址紀錄裡
    try:
        # requests 會自動跟隨 GAS 的 302 轉址，取得真正的執行結果
        r = requests.post(WEBAPP_URL, json=payload, timeout=TIMEOUT_SECONDS)
        r.raise_for_status()
        return r.json()
    except Exception as e:
        return _fail(f"無法連線 ERP，訂單是否成立未知，請人工到試算表確認：{e}")


if __name__ == "__main__":
    mcp.run()  # 預設使用 stdio 傳輸

函數上方三引號內的文字會自動成為工具的 description；Annotated[..., Field(...)] 會自動轉成 inputSchema。例如 quantity 會變成 {"type": "integer", "minimum": 1, "maximum": 100}，和第 8.1 節手寫的規格一致。ToolAnnotations 則是給 Host 參考的「工具性質標籤」（例如唯讀），MCP 規格要求 Host 對來源不可信的伺服器，不得把這些標籤當真；它是提示，不是保證。

🔍 驗收重點（不懂語法也能檢查） - MAX_ORDER_QTY 是否在最上方，而不是埋在函數裡？ - 查庫存是否標示 readOnlyHint=True、下單是否標示非唯讀？（第 8.2 節的分類） - 連線失敗時，回傳的是錯誤訊息，還是一個「看起來合理」的數字？ - 密鑰是從環境變數讀取，而不是寫死在程式碼裡？錯誤訊息裡有沒有不小心印出密鑰？ - 下單工具的說明，是否要求 AI 先複述內容並取得同意？

實驗③的算式（成本為歐元，售價為台幣）：

毛利率 = 1 − 加權單位成本(EUR) × 匯率 ÷ 售價(TWD)
匯率 31.5：1 − 112 × 31.5 ÷ 4,200 = 1 − 3,528 ÷ 4,200 = 16.0%
匯率 35.0：1 − 112 × 35.0 ÷ 4,200 = 1 − 3,920 ÷ 4,200 =  6.7%

以第 1.1 節的底線 15% 來看，前者放行、後者亮紅燈。ERP 的業務入口網頁以帳務匯率 35.0 估算，A 款賣 NT$ 4,200 會顯示「🛑 預估毛利率 6.7%」，與第 6.3 節儀表板的算法一致。AI 缺資料時應該問，不應該猜；若要讓 AI 自己算，正確做法是再提供一個查匯率的工具（第 1.3 節的匯率來源），而不是讓它憑印象填數字。

實驗④⑤說明了兩件事：

  1. 參數規格只保護「走 MCP 這條路」的請求。 繞過 MCP 時，minimum: 1 完全不起作用；真正擋下 −5 的是後端 apiSubmitSalesOrder() 的數量檢查。如果後端沒有這段檢查，−5 不大於庫存 25，就會被當成合法訂單，庫存反而增加。防呆必須放在後端，前面的每一層都只是額外保護。MCP 規格本身也要求 Server 驗證所有輸入並做好存取控制，但這只約束 MCP Server，管不到被直接呼叫的 Web App。
  2. 網址不是密碼，密鑰才是。 存取權設為「所有人」、執行身分為「我」，代表任何人都連得到這個網址；擋住外人的是 token。但共用密鑰仍是入門做法：所有呼叫者用同一把，外流後任何人都能以你的帳號權限查成本、下訂單，系統也分不出是誰下的單。本節的系統適合課堂練習或個人使用，正式營運資料應改用需登入的 OAuth 授權（第 13.2 節）。

本節小結

  1. MCP 是 Anthropic 提出、現由 Linux 基金會旗下組織治理的開放協定，把 N×M 的客製串接變成 N＋M 的標準介面。
  2. Host 是你用的 AI 應用，Server 是包裝系統能力的小程式；Server 可提供 Tools（執行動作）、Resources（提供資料）、Prompts（工作範本）。
  3. 本節用兩層包裝接上 ERP：GAS Web App 讓試算表能被呼叫，MCP Server 加上名稱、說明與參數限制，讓 AI 能正確且有限度地使用。
  4. 參數規格擋不住繞過 MCP 的請求：防呆一定要放在後端；Web App 要以密鑰把關，且「沒設定密鑰就全部拒絕」。共用密鑰只是入門做法，正式營運資料要用需登入的授權。

柒、練習

  1. 改數字（5 分鐘）：公司規定 AI 單筆最多只能代下 20 台。請修改 erp_mcp_server.py 的哪一行？改完後重新啟動 MCP 伺服器，再要求 AI 下 25 台，會在哪一層被擋下？（提示：試算表根本不會收到這個請求。）
  2. 加功能（20 分鐘）：讓後端擋下低毛利訂單。在 apiSubmitSalesOrder() 的數量、單價檢查之後加一條規則：單價低於「加權單位成本 × 帳務匯率 ÷ (1 − 毛利底線)」時，回傳 success: false 與「毛利低於底線，需主管核准」，不扣庫存。帳務匯率與毛利底線沿用 ERP 最上方既有的常數 DASH_FX_RATE、MIN_MARGIN，不要另外寫一份。先在第參段規格表加一列，再修改 Prompt 請 AI 產生程式碼；用預設資料驗證：A 款門檻為 112 × 35 ÷ 0.85 ≈ NT$ 4,611.76，單價 4,200 應被擋下、4,700 應放行（預估毛利率 16.6%）。想一想：這條規則也會擋住業務入口網頁與 CRM 的下單，這是好事還是壞事？
  3. 管理反思（討論）：(a) 本節的共用密鑰比「有網址就能用」安全多少？它還有哪些弱點（密鑰外流後怎麼辦、能不能分辨是誰下的單）？(b) 某航運集團每年花大筆預算維護多套 AI 專用外掛，以串接自家 ERP。請從長期維護成本、被單一廠商綁住的風險、資安責任歸屬三個角度，說明改用 MCP 標準的利弊。再想一想：公司的 ERP 若提供 MCP Server 給供應商的 AI 使用，check_erp_inventory 應該回傳哪些欄位、隱藏哪些欄位？
